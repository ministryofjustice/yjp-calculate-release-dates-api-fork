# C4 diagram

Shows architecture at increasing zoom: **Context** (the system, its users and the external systems it talks to), **Container** (the deployable/runnable units inside it: apps, services, databases, queues, front-ends) and **Component** (the main building blocks inside one container). Skip the fourth level (Code); a class diagram covers it.

## How to search

C4 is about **what runs where and what talks to what**. That evidence lives mostly in infrastructure and wiring, not in function bodies.

1. **Find the containers (deployable units).** Look in:
   - `docker-compose*.yml` and `Dockerfile`s
   - k8s/Helm manifests and Terraform/Pulumi/CDK
   - `Procfile`, serverless configs
   - monorepo workspace files (`package.json` workspaces, `pnpm-workspace.yaml`, `go.work`, Maven modules)
   - separate `apps/` and `services/` folders, and front-end projects
   Each separately started process or datastore is a container. A single-process app with a database is two containers.
2. **Find the external systems and the technology on each connection.** Look in:
   - environment and config: `.env.example`, `config/*`, `process.env.*`, `os.environ`, `settings.py`
   - SDK imports and client classes (`stripe`, `nodemailer`, `@aws-sdk/*`, `redis`, `kafkajs`)
   - HTTP base URLs
   - queue and topic names
   Each one becomes an external system, or a container if it's yours. Note the protocol (HTTPS/JSON, SQL, SMTP, AMQP, gRPC).
3. **Find the people (actors).** Look at auth roles, the admin vs customer route split, and front-ends and their audiences.
4. **Components, only if asked or useful.** Inside one container, take the main modules or layers from the folder structure and the composition root (route mounting, DI container, `app.ts`). Examples: routers/controllers, services, repositories, clients. Connect them by real imports and calls.
5. Read the `README` and any `docs/architecture*` for names and purposes, but verify them against the code. Docs go stale.

## How to draw

- Mermaid C4 syntax: `C4Context`, `C4Container` or `C4Component`, and `title ...`.
- Elements:
  - `Person(id, "Label", "description")`
  - `System(...)` and `System_Ext(...)`
  - `Container(id, "Label", "Technology", "description")`, `ContainerDb(...)`, `ContainerQueue(...)`
  - `Component(...)`
  Group them with `System_Boundary(id, "Label") { ... }` or `Container_Boundary(...) { ... }`.
- Relationships: `Rel(from, to, "what", "protocol/tech")`. Use `BiRel` only for genuine two-way traffic.
- Keep labels short; the description slot is for one short phrase.
- Use `UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")` if the layout gets cramped.

**Split by level.** By default, produce a **Context** and a **Container** diagram as separate files (`<subject>-c4-context`, `<subject>-c4-container`).

Add a **Component** diagram only when:
- the user asks about a service's internals or for the component level; or
- there's just one app container, so Container alone says little.

In the second case, make **one** Component diagram for that container. Split it only if it would have more than about 15 elements, and then by functional area.

Keep each diagram under about 15 elements.

**Layout budget.** Mermaid's C4 renderer has little automatic layout, so some crossing lines are normal. Improve it cheaply:
- declare elements in the order you want them to appear, top-left first;
- put external systems last;
- use `UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")`;
- use `UpdateRelStyle(from, to, $offsetX="..", $offsetY="..")` for a label that collides.

Re-render at most two or three times for layout. Then accept minor crossings, as long as every label is still readable. Don't switch to flowchart syntax to get a nicer layout: the user asked for C4.
